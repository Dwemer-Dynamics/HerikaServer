# Actor identity in event participants

Status: wired end to end on the server. Ingestion, stored roles, keyed dynamic registration, context, speech, memories, diaries and books, relationships (runtime, worker, NPC manager and editor saves), response/action identity, Director, SNQE, letter couriers, schedules, Book Read comments and playthrough save/transfer use exact keys. The paired CHIM client sends identity for player dialogue, `log()` events, observations, speech and rechat. The remaining name-based paths are listed in [Still name-based](#still-name-based); legacy unkeyed rows stay unassigned. See [Pipeline status](#pipeline-status).

## Keys

| Key | Meaning |
|---|---|
| `ref:<plugin>\|<local>` | A placed reference. `<plugin>` is the plugin file name with ASCII letters lowercased (`skyrim.esm`); `<local>` is the eight-digit uppercase local FormID (`0001BDE8`, at most `00FFFFFF`). |
| `player` | The player character. |
| `narrator` | The Narrator. |
| `dyn:<uuid>` | Client-assigned persistent key for a dynamic (`FF`) actor, saved by the plugin: lowercase 8-4-4-4-12 hex, not the nil UUID. |

Keys must already be canonical; anything else is treated as having no identity. Runtime FormIDs, `FF` IDs, base IDs, `runtime:` selectors and display names are never keys. Unrelated actors with the same name keep different keys. The server never assigns a key by matching names.

## Stored format

`eventlog.people` stays a text column. Identity format 2 is a JSON array written without leading whitespace:

```json
[{"name":"Astrid (busy)","id":"ref:skyrim.esm|0001BDE8"},{"name":"Lydia"}]
```

- `name` is the display name recorded for this event, including a status suffix such as ` (busy)`, ` (hostile)`, ` (in combat)` or ` (restrained)`. It is a snapshot and is not rewritten after a rename. It must be non-blank, at most 256 characters, and contain no control characters. `|` is allowed: the object keeps the name apart from the key.
- `id` is optional. Without it the participant is name-only and unresolved.
- Repeated keys keep the first entry. Name-only entries are deduplicated by exact name.
- Text that is not a JSON array, including legacy `|Name|Other|` lists and bare names, is legacy name-only data. Legacy lists still split on `|`.

## Reading stored rows (tolerant, display only)

`chimParseEventParticipants()` reads history as it is and never rewrites it:

- An entry keeps its key only if it is an object with a valid `name` and a canonical `id`. PHP and `public.chim_eventlog_actor_keys()` apply the same rule, so they report the same keys.
- Objects with an invalid `name` are skipped. Objects with an invalid or missing `id` are shown name-only. String entries are shown name-only.
- Text starting with `[` that PostgreSQL `jsonb` rejects, such as malformed JSON or a `\u0000` escape, has no keys. It is shown as a legacy name list, because legacy writers may store a bare name that starts with `[`.
- No key is ever guessed from a name, a runtime ID or a malformed entry. Known residual differences: a document nested deeper than PHP's 512-level `json_decode` limit parses only in PostgreSQL. A number beyond PostgreSQL's `numeric` range, or nesting past its stack limit, parses only in PHP. Writers never produce either.

## Strict boundaries

Client ingress and serialization never accept a partial audience. They throw `ChimEventIdentityException` (an `InvalidArgumentException`) with a fixed `reason` and, where it applies, the zero-based participant `index`:

| `reason` | Cause |
|---|---|
| `unsupported_version` | `identity_version` is present but is not the integer `2` |
| `participants_invalid` | `participants` is missing or is not a JSON array |
| `participant_invalid` | An entry is not an object, has no `name`, or has fields other than `name` and `id` |
| `participant_name_invalid` | `name` is not a valid name |
| `participant_id_invalid` | `id` is present but not a canonical key; `null` counts as provided for client payloads |

The caller must reject the event explicitly. It must not fall back to legacy name routing.

## Client payload capability

A client event opts in by adding both fields to its JSON event metadata:

```json
{"identity_version":2,"participants":[{"name":"Astrid","id":"ref:skyrim.esm|0001BDE8"},{"name":"Bandit"}]}
```

`chimEventIdentityParticipants($payload)` has three results:

- `null`: `identity_version` is absent. The client is legacy and `participants` is ignored.
- A list of participants, possibly empty: every entry was valid. Omitting `id` leaves that participant unresolved.
- `ChimEventIdentityException`: the event must be rejected.

## Database

PostgreSQL uses `public.chim_eventlog_actor_keys(people)` from `data/eventlog_actor_identity.sql`, with the partial GIN index `idx_eventlog_actor_keys` covering rows that start with `[`. The function never raises on legacy or malformed text. The index depends on it, so do not change its results in place.

`debug/db_updates.php` applies the file under version key `eventlog_actor_identity` `20260930002`. It reruns this idempotent file if the function, index or role columns are missing. `lib/runtime_bootstrap.php` requires that version, the `eventlog` table and every listed object before a request continues. Otherwise it runs the database updates first. Consumers can therefore rely on the SQL once bootstrap has run. Both gates read one object list in `lib/identity_schema_readiness.php` covering the eventlog, memory, action/mood, diary and task-owner identity migrations, including appended `memory_v` columns. Update that list with the SQL files. A column with an unexpected type is logged by `db_updates.php` and is neither rerun nor converted.

Playthrough saves, based on `lib/schema_clone_function.sql`, `lib/playthrough_upgrade.sql`, `lib/playthrough_selection.sql` and `lib/playthrough_transfer.php`:

- Capture clones selected tables with `CREATE TABLE ... (LIKE ... INCLUDING ALL)`, so saves made after this migration carry the index. It still references `public.chim_eventlog_actor_keys`.
- Saves made earlier, and imported archives, have no index. Imports build raw tables from column definitions only. Their private stages copy the saved table, so they have no index either. Nothing queries a stage by actor key.
- Restore, and import validation's rolled-back restore, delete and insert rows in the existing `public.eventlog`. PostgreSQL maintains the live index for inserted rows. Because the function never raises, malformed history cannot fail a restore.
- Neither the table policy nor the playthrough SQL API changes.

Linked references share memories, relationships and settings through the existing profile owner. Each event still records the physical key of each participant.

## Pipeline status

### Wire contract

- **Event metadata (request field 4, or field 5 for `bored`).** `chimEventIdentityFieldIndex()` selects the field by request type: `bored` keeps field 4 as its seed actor and carries identity in field 5; `_speech`, `infonpc_close`, world events and player dialogue use field 4. `chimDecodeRequestEventIdentity()` decodes it. The field is a base64 JSON object (for field 4, the player routing snapshot). An opted-in event adds `identity_version: 2` and `participants` (`[{"name", "id"?}]`), and optionally `speaker_key`, `listener_keys` (list) and `target_key`. Role keys are provenance only and never add anyone to the audience. A field 4 that is not a base64 JSON object, or has no `identity_version`, is legacy.
- **Registration (`addnpc` and `addbgnpc`).** Both messages are `Name@Base@gender@race@refid@…` with the same layout in the client (`Papyrus.cpp` registration, background registration, and save-load re-registration in `Plugin.cpp`): index 41 mods, 42 factions, 43 class, 44 `refid_source`, 45 `actor_key`. `actor_key` is `ref:…` for placed actors (must equal the key of the verified field 44 source), `dyn:<uuid>` for dynamic actors (only valid without a source), or empty for legacy. An invalid or mismatched value skips the registration. The registration has no field 4 actor key.
- `main.php` validates field 4 with `chimDecodeEventIdentityField()` before any eventlog write. Invalid opted-in events get HTTP 422 and `ERROR: invalid event identity (<reason>)`; role failures use `role_key_invalid:<field>`. Nothing falls back to legacy name routing.

### Stored roles

`data/eventlog_actor_identity.sql` (version `20260930002`) adds nullable `eventlog.speaker_key`, `eventlog.listener_keys`, `eventlog.target_key`, `speech.speaker_key` and `speech.listener_keys` (`listener_keys` is a JSON array of keys). `NULL` means "not captured" and is never backfilled from names. Rerunning the file keeps rows and roles unchanged.

- The request's own event gets the client's audience and roles: `logEvent()`, the request row in `main.php`, and every `processor/comm.php` row built through `chimIncomingEventColumns()` (same type and timestamp as the request). `_speech` stores the client's `speaker_key`/`listener_keys` on the `speech` row.
- Other rows written while handling a request (narrator welcome, model toggle, time skip, housekeeping) do not inherit its audience or roles; `resolvePeopleForIncomingEvent()` uses the capture only with the request's type and timestamp.
- The current actor's own reply lines (`chimCurrentActorUtteranceIdentity()`) store the captured audience, the replying row's physical key as `speaker_key` (added to the audience if missing), and no listener or target. Without a keyed selected row they keep the forced name list, name-only, with no roles. They never inherit the player's roles.
- A forced legacy name list stays name-only. No name, including the player's or "The Narrator", becomes a key; callers that know keys pass a format-2 list. An explicit empty v2 audience is stored as `[]`.

### Typed principals and context

- `player` and `narrator` come only from typed context: a client capture, or a caller that is building the player's or Narrator's own context and passes `CHIM_ACTOR_KEY_PLAYER`/`CHIM_ACTOR_KEY_NARRATOR`. A physical row always wins, so an NPC named like the player or "The Narrator" keeps its own key.
- `buildHistoricContext()`/`DataLastDataExpandedFor()` and `DataLastDataExpandedForNPC()` take an optional selected row/principal. `main.php` passes the request's selected NPC row, Dynamic Profiles passes the candidate row (Narrator: `narrator`), the player diary passes `player`, and Background Life target summaries pass the target row. Only exact keys of that row and its explicitly linked references match; legacy name-only rows never match an actor-specific context.

### Dynamic actors

- `addnpc`/`addbgnpc` with a `dyn:` key select the row by `metadata.actor_key` only (never by name or FF slot) and create it through `createProfile()` with that key; its `md5` selector is `md5(<dyn key>)`.
- When the FF runtime slot is still held by another row (a recycled reference), that row only releases the slot. Its name, `md5`, metadata, own `dyn:` key and history stay; a keyless row records its selector in `metadata.detached_selector` so later edits never fall back to a name hash. Release, bind and create commit together under a table lock; any failure rolls all of it back. No LLM or network work runs inside.
- A legacy or keyless same-name/same-slot row is never adopted by a `dyn:` registration and its data is not inherited.

### Memories

`data/memory_actor_identity.sql` (version `memory_actor_identity` `20260930001`, applied by `debug/db_updates.php` and required by `lib/runtime_bootstrap.php`) is additive and idempotent:

- `public.chim_identity_audience_keys(text)`: sorted exact keys of a format-2 audience; `NULL` for legacy, bare-name or malformed text, `'{}'` for a captured empty `[]`.
- `speech.audience`: the `_speech` client's captured format-2 audience (`[]` when captured empty, `NULL` for legacy). `companions` keeps the legacy name list unchanged.
- `memory.audience`, `memory.owner_key`: set only by callers that know the key (`logMemory(..., $ownerKey, $audience)`; the player diary passes `player`, auto-diary the request's selected row). Never derived from `speaker`.
- `memory_summary.audience_keys`, `partition_key`, `source_refs` (`[{"t": table, "id": rowid}]`).
- `memory_v` keeps its six columns and appends `source_table`, `source_rowid`, `audience`, `audience_keys`, `speaker_key`, `listener_keys`, combined with `UNION ALL` (uids overlap across tables). The older narrower definition in `db_updates.php` only runs before `memory_v` `20251122001`.

`PackIntoSummary()` partitions source rows by their exact sorted audience keys before packing, so every summary's audience saw all its sources; legacy rows form an unresolved `legacy` partition. Each partition resumes after its own newest summary. The summary utility chains a previous summary only within the same partition, `fixcomp` only fills legacy rows, and individual summaries for a keyed row use only global summaries whose audience contains its own key (`partition_key individual:<key>`).

Every actor-specific memory read resolves a typed principal with `chimMemoryActorScope()`: an explicit physical row or reserved principal, else the request's selected row when it is this actor, else `narrator` only when `main.php` typed the request as a narrator request (`CHIM_CONTEXT_ACTOR_PRINCIPAL`, set by request type/profile selector, never by name). `offerMemory()` resolves it before any name handling and passes it through `DataSearchMemory()`, `DataSearchMemoryByVector()`, `DataSearchMemoryByVectorFromContextKeywords()` and `lastKeyWordsContext()`; short-term memory, the middle-term generator and the legacy txtai `queryMemory()` use the same scope.

- `dataGetMemoryCompanionConditionSql()` filters inside `WHERE`, before ranking and `LIMIT`: a physical row reads summaries whose `audience_keys` overlap its own and explicitly linked keys. A missing or unkeyed principal reads nothing (`FALSE`); legacy (`NULL` audience) summaries stay stored and displayable but are never injected. Only the typed Narrator keeps the global policy (`TRUE`, or with `NARRATOR_ONLY_DIARY_ACCESS` non-diaries plus diaries whose audience has `narrator`). A physical NPC named "The Narrator" is that NPC.
- Individual memory is enabled by the selected row's effective `extended_data` (shared from the profile owner while linked). New individual summaries use `scope`/`partition_key` from the row's own key and are only generated for keyed rows; legacy `scope=<name>` rows are never read. Readers match `scope IN (group keys)`, so linked references share and lose them on unlink.
- `middle_term_memory` is shared while linked. The generator reads summaries whose audience overlaps any current group key (including events only a non-owner witnessed) and records per-entry provenance in `extended_data.middle_term_memory_provenance[<gamets>]`: `{v:1, origin:"generated", source_keys, group_keys, profile_binding, owner_npc_id, summary_rowids, text_sha256}`. `source_keys` are the group keys that actually witnessed (or own the individual scope of) a used summary, plus the predecessor digest's `source_keys`. It commits only if `chimNpcProfileBinding()` and the sorted group keyset still match what it read, through `updateExtendedKeysById(..., $binding)`.
- Every prompt consumer and the short-term hightide use `chimMiddleTermLatestDigest()` / `chimMiddleTermValidDigests()` (`lib/core/npc_profile_sharing.php`): an entry is usable only with v1 generated provenance, an unchanged text hash, and every `source_key` in the requesting row's current group (`chimNpcProfileActorKeys()`). Unprovenanced (legacy), edited or post-unlink contaminated entries stay stored for display/admin, never reach a prompt and never advance the hightide; the generator continues from the latest usable entry, so an unlinked owner rebuilds from its own sources. A rebuilt entry that lands on the gamets of an unusable entry moves that entry, with its provenance, to `middle_term_memory_dormant` instead of overwriting it. Callers: `main.php`, `lib/director_scene.php`, `DataShortTermMemoryFor()`, Background Life `main.php`/`main_lw.php`/`helpers.php`/`background_action_handler.php`, `ui/cmd/ai_profile_generation_service.php` (dynamic profiles), the debug copies, and the generator's previous digest. The three keys are in `CHIM_SHARED_NPC_EXTENDED` and the NPC override reserved list, travel in `core_npc_master.extended_data` with playthrough saves and transfers, and rollback restore trims provenance with its digests.
- Manual digests: an edited digest no longer matches `text_sha256`, so a hand edit without new provenance is display-only. The Prisma NPC manager (`ui/api/chim_npc_manager.php` save, `middle_term_latest`) stamps provenance itself from the row it loaded by id under the owner lock and current `profile_revision`: `origin: "manual"`, `source_keys` = `group_keys` = `chimNpcProfileActorKeys()` of that row, its binding and owner id, no summary rowids. The replaced entry moves with its provenance to `middle_term_memory_dormant` once (clearing the text does the same); a manual draft with the same owner and `group_keys` is replaced without archiving, so repeated edits do not grow the list, while a generated, legacy or other-group (pre-link/unlink) entry is always kept. The save commits only if `extended_data` is unchanged since its locked read (409 otherwise). The generator discards its result if the latest usable digest changed during the model call (manual edit or another run) and writes through `NpcMaster::update()` with a `_commit_guard` comparing `extended_data` under the row locks, so a concurrent manual save is never overwritten. Unchanged text is a no-op. Request-supplied provenance/dormant/`extended_data` are never read. `chimMiddleTermDigestValid()` accepts `generated` and `manual`; an unkeyed legacy row gets empty `source_keys`, so its manual digest stays display-only. The legacy `ui/core/npc_master.php` form still posts raw `extended_data` (web pass S9b).
- NPC manager API (`ui/api/chim_npc_manager.php`): list/detail cards carry `actor_key` (`chimNpcRowActorKey()` of the physical row, null for legacy). Every operation accepts `expected_actor_key`; a mismatch (row reuse, forged key) is 409, as are a stale `profile_revision`, link/unlink or playthrough switch. History reads format-2 rows whose keys overlap the row's profile group, inside `WHERE` before `LIMIT`; legacy name-only rows are listed read-only (`legacy_unassigned`) only while the name is unique and are never deletable. Recipients are `{name,id?}`. `inject_event` writes format 2 with each recipient row's own physical key (checked against `recipient_expected_keys`) and refuses unkeyed rows. Relationship saves validate against the stored map under the owner lock: existing edges keep map key and target (only `aff`/`type`/`note`/`custom_info` change), untyped legacy edges are kept as stored even if omitted or edited, new edges must be `Player`, an actor selected by `target_npc_id` plus that row's own `card.actor_key` (its current effective key is also accepted) and stored under the effective key from `RelationshipManager::targetIdentityForActor()`, so a linked member's card writes the keeper's shared edge (label from the selected row, id stripped; self/own-group targets and a duplicate of an existing effective edge are 422; the target's binding and keys are rechecked under row locks in the write, 409 after a concurrent link/unlink), or a concept with `key === label` that is not actor-shaped, Player, or an existing key (422 otherwise). `ui/api/npc_schedules.php` applies the same `expected_actor_key` 409 check on the physical row and never reroutes to a keeper; save/cancel/retry/delete recheck it on the row locked (`FOR SHARE`) inside the write transaction after the clock and NPC schedule locks (`chimScheduleGuardActorKey()`). Worker callers without an expected key keep their own locked owner-row guard.
- Speech readers (`DataLastDataExpandedForNPC()`, `DataSpeechJournal()`, `lastKeyWordsContext()`, Background Life workers) use `chimBuildSpeechActorKeysWhereClause()`: `speaker_key` or captured `speech.audience`. `GetFirstInteraction()`/`GetLastInteraction()` use captured roles (`speaker_key`, `listener_keys`) between `player` and the actor. `DataLastDataFor()` uses exact eventlog keys.

Participants without a registered physical key, and legacy name-only rosters, are skipped. Each row gets its own cooldown (`DIARY_LAST_TIMESTAMP_KEY_<md5(key)>`), selected-row context and `owner_key`; `generateFollowerDiary()` requires a typed row or the typed Narrator and restores the request's selected row afterwards. Letters stay unresolved. First-met lookup is by `owner_key`.

### Relationship edges

`extended_data.relationships` stays one map per source, inside `CHIM_SHARED_NPC_EXTENDED`, so a linked source reads and writes the keeper's map and its own dormant map is preserved until unlink.

- Actor edges are keyed by the target's canonical physical key (`chimNpcRowActorKey()`) and carry `target: {kind: "actor", key, label}`. While the target is linked its key is the keeper's (`RelationshipManager::targetIdentityForActor()`), so every linked reference shares one edge. The dormant edge under the member's own key is not merged, averaged or deleted (the keeper's edge wins), and it is live again after unlink.
- The player edge stays `Player` (`kind: "player"`). Player aliases fold only in name keys, never in actor keys. An NPC named after the player, "Player" or "The Narrator" stays a physical actor.
- Name keys without an actor target are unattributed legacy data (stored, shown raw by `getRelationships()` for a later explicit user attribution) or explicit `target.kind: "concept"` entries. They are never assigned to an actor by name, even when one row has that name today, and runtime readers never show unattributed legacy entries. Concepts are read only when explicitly classified (`setRelationship(..., kind: 'concept')`); unknown names never become concepts.
- Runtime readers and writers resolve typed targets with `RelationshipManager::resolveTargetIdentity()`: an exact row/id, an actor key, a rendered `Label [key]`, a captured roster row (`DataCloseRangeActorRoster()`), the player, or a bare name only when its rows share one effective key. Same-name bare labels are `ambiguous` and refused. `getRelationship()`, `buildContext()`, `buildDirectorContext()`, `parseChanges()`, `setRelationship()`/`adjustRelationship()` and transitive inference read/write only typed edges. Prompts render same-label actors as `Label [key]`; `#REL:`/`#TYPE:` accept that form. Dedicated-model output maps only to the captured endpoints of that evaluation, with a shared label refused unless the key is named; uncaptured registered actor names are refused; other names stay name-keyed (display-only).
- Both `relationship_eval_queue` and `relationship_init_queue` store `_rel_capture` {`bindings`, `keys` (endpoint and keeper), `timeline`} and a random `queue_token` assigned on every enqueue/upsert, so an identical replacement in the same second is a different job. `timeline` is the playthrough runtime generation file (`log/playthrough_runtime/generation`, read fresh) plus `DYNAMIC_PROFILE_CLOCK.epoch`. The worker drops unbound legacy jobs and jobs whose capture is no longer current before the model. Without holding a transaction across the model call, it commits through `NpcMaster::update()` with `_profile_binding`, `_expected_bindings`, `_expected_keys` (physical keys of source, target and keepers) and `_commit_guard` (claimed token + full capture re-check). `chimNpcWriteSharedProfile()` checks these with the rows locked, and uses a savepoint when the caller already holds a transaction. Ack, abandon and retry compare the token. Init analysis runs under the binding captured at enqueue.
- Editors: `ui/api/chim_npc_manager.php` and the legacy form handler (`npc_save_handler.php`) keep each stored edge's server-owned `target` (a changed posted target is a stale form and is refused), accept a new actor edge only with the selected row id and key (`RelationshipManager::validateNewActorTarget()`, rechecked under row locks), require explicit `concept` targets, and keep plain-name entries as legacy display-only. `relationship_editor.php` shows typed targets by label without exposing keys. The `analyze_relationships` preview stays name-keyed by design: its history and `counterparts` come from a name match on `people` (`chimRelBuildEventBaseline()`) and its targets are LLM-written names, so no exact target identity exists to bind; its entries save only as legacy display-only rows and are never resolved to a typed edge by name. Postrequest speech fallback uses only this speaker's captured `speaker_key`/single `listener_keys`; the NPC-to-NPC listener id still falls back to `getByPromptIdentifier()` when no captured listener exists.

### Response identity (v1)

Streamed output keeps `label|queue|payload`; actor-bearing lines append a fourth field, standard base64 of `{"response_identity_version":1,"actor":{"id","refid"},"listener":null|{"id","refid"},"targets":[{"arg","id","refid"}]}` (`lib/core/response_identity.php`). The actor is the selected row's own key and runtime RefID (a physical row named The Narrator stays physical), the typed narrator `{"id":"narrator","refid":null}` or the typed player `{"id":"player","refid":"00000014"}`; unkeyed legacy rows keep three fields. The listener is a decorated `Name [RefID: X]`, an actor key, or a bare name matching exactly one key captured on the request (field 4/5 roles); otherwise null. Targets name only the actor arguments the client resolves for that command (`chimResponseCommandActorArgs()` mirrors the client table), resolved exactly; non-actor arguments carry none. Labels and payloads never carry `|` or newlines; a contradictory key/RefID drops the line instead of downgrading it. Producers: chat ScriptQueue (NPC, inline narrator, player TTS), `Halt`, `ToggleModel`, `queueFunctionExecutionCommand()` and the JSON connectors' native tool calls, and Director scene lines (`actor_identity`/`listener_identity`). Action post-filters reattach the original field to rewritten actions, and server-executed post-filters select their actor by the envelope key. `RefreshNPCVoice` carries the refreshed row.

Delayed output keeps the identity captured at enqueue, with no schema change: the `responselog` insert hook (`chimResponseQueueAttachIdentity()`, called from `sql::insert`/`insertReturningId`) writes the fourth field into `text` for `queue|payload` actions, or appends `|<field>` to sanitised text otherwise, so `actor|action|text` is already the four-field line. `rolemaster` system commands carry the typed narrator plus exact command targets; an unresolvable decorated label drops the row; other unkeyed labels stay three fields. `comm.php` emits rows through `chimResponseDequeueLine()`, which rejects a row whose captured actor, listener or target key no longer resolves to the same RefID (stale or recycled `FF` references) instead of re-deriving it from current globals. Signed 32-bit decimal role arguments (`spawnCharacter` arg 4, `spawnItem`/`spawnBook` arg 2) normalise to 8 hex digits.

ScriptProxy commands (`SkyrimCommandBuilder::send`) declare `"actor_identity_version":1,"actor_targets":{"<param>":{"id","refid"}}` when every actor parameter of that command range resolves exactly (the player, or a keyed row owning that RefID): Actor `targetObjectFormId`/`akTarget`/`akOther`/`akCriminal`/`aTarget`, ObjectReference `targetObjectFormId`/`akActivator`, ActorUtil `targetObjectFormId`/`akActor`. Faction, FormList and EffectShader targets, spells, idles, items, packages and markers are forms and never bind. Declared values are rewritten to `0x` + 8 hex digits; with any actor parameter unresolved nothing is declared. Every `|` in the JSON, including inside `ref:` keys, travels as `|`. The envelope itself carries no `@` targets for ScriptProxy.

The Director selects its cast from the captured close-range roster (`chimDirectorCastRows()`): each registered keyed participant keeps its own row, and namesakes are offered to the model as `Name [RefID: XXXXXXXX]`, so a same-name pair can both speak and address each other; legacy rosters without keys fall back to a unique name row. Actions store `speaker_identity` and dispatch through that key. Each cast row's id, key and RefID are captured before the LLM/TTS delay (`chimDirectorCastBindings()`); publication re-reads them inside its transaction and aborts the scene if any moved (`chimDirectorAssertCastCurrent()`). Pending history rows store the cast plus the typed player as format-2 `people`, with `speaker_key` and `listener_keys` from the captured bindings (`chimDirectorLineIdentity()`). A physical NPC named "The Narrator" is labelled with its RefID like a player namesake, so the bare label `The Narrator` always means the reserved narrator, which joins only the action catalog and never replaces a cast label. Rechat resolves decorated speakers and hints exactly: a decorated hint naming another reference is a namesake, not the speaker, and the selection stays decorated. A rechat payload carrying `rechat_identity_version` or a `speaker_key` member (any value) takes the identity path (`chimResolveIdentityRechatTarget()`); only payloads with neither keep the label path, which still leaves an ambiguous bare name unassigned. The version must be the integer 1. The speaker is the `speaker_key` row or typed `narrator` only: missing, empty, malformed, `player`, unknown or ambiguous keys, or a key contradicting the captured field-4 `speaker_key`, refuse the rechat; captured `player` data on a narrator rechat is ignored. A present `listener_key` is the exact listener and must be a valid known key, otherwise the rechat is refused; the target hint then only repeats that listener. Without `listener_key`, an empty listener hint means no listener, a bare hint never resolves, and only a decorated static (`ref:`) hint whose reference belongs to a key captured on this request is used; keyless FF hints stay unresolved because FF references recycle. The audience is the latest keyed conversation row between the two principals (key filters before the row limit; a talk-target name only confirms a peer on a row without captured listener roles, and only when no participant shares its name). Actor state comes from each key's own captured state suffix, `active_agents` labels map to one key each, and the per-mode candidate order and directly addressed sleeping rule are unchanged. A physical row named "The Narrator" is an ordinary keyed candidate; `chimSwitchActiveNpcProfile()` switches by key and refuses a key re-bound to another row since resolution. The budget session key uses canonical members plus the interaction generation. The ScriptQueue listener rotation expands captured physical listeners into decorated identifiers (excluding the speaker's own row), so the listener envelope resolves. `DataActorHasDied()` matches captured deaths by `target_key` (text only for legacy rows without one) and `getGametsLimitFor()` uses the actor's exact audience.

Proposed client C10 ordinary-command actor arguments (not emitted by the server yet: the current client refuses targets on unlisted arguments): `Attack`, `Follow`, `Inspect`, `MoveTo`, `Brawl` target arg 0; `GiveItemTo`, `GiveGoldTo`, `CastSpell` carry the actor in their JSON parameter object's `target` property, which an `@` index cannot address, so they need a named-property binding like ScriptProxy. `CheckInventory`, `TakeASeat`, `StopWalk` and `TravelTo` take items, blanks or places. When the client table grows, extend `chimResponseCommandActorArgs()` in the same change.

### Issued actions, moods and game data

`actions_issued.actor_key` and `moods_issued.actor_key` are nullable owner keys (`data/action_mood_actor_identity.sql`, version `action_mood_actor_identity` 20260930001; `lib/runtime_bootstrap.php` checks both partial indexes). Only an exact binding stamps a key: an action line's identity envelope whose key still owns its RefID (`chimResponseActionActorKey()`), the selected physical speaker (`chimResponseCurrentActorKey()`), a Background Life worker row, or a Director `speaker_identity`. Name-only actions, `PATCH_ACTION_ALL_ACTORS` and typed principals leave NULL; SNQE `actions_issued` rows take the key of the quest NPC's resolved row (`snqeActionActorKey()`); Background Life NPC creation stamps the key of the row bound to its own `spawned@<name>@<FormID>` status (`chimSpawnStatusRefids()`/`chimSpawnedActorRow()`), refusing several spawned RefIDs or a RefID now held by another name. SNQE `CheckNPCSpawn` stores the same binding as `actor_refid`/`actor_key` in quest data (`snqeQuestNpcRow()`); quests saved before binding keep the unique-name lookup; a unique name never grants ownership. SNQE presence uses the bound key in the latest `infonpc_close` participants (`DataCloseRangeActorRoster()`), deaths use `target_key` (`snqeQuestNpcHasDied()`), and `SpawnNPC`/`CreateNPC` accept an earlier spawn or existing profile only by binding or an unshared name. The client role commands `moveToPlayer@`, `Suggestion@`, `Instruction@`, `TravelTo@`, `CombatPlayer@` and `Despawn@` take an agent argument that is either a bare name, accepted only when exactly one active agent has it, or the exact `Name [RefID: XXXXXXXX]`, bound to that active agent only with no name fallback (`AIAgentManager::getAgentByName`, `CaptureRoleCommandTargets`). SNQE sends a bare name when no other profile shares it (case-insensitive) and otherwise the decorated RefID of the quest NPC's resolved row (`snqeQuestNpcCommandTarget()`); an unbound, stale, empty or zero RefID sends nothing. The letter courier binds its own spawn RefID the same way and stores it in `bgl_letters.courier_refid` (version `bgl_letters` 20260930001), so moveToPlayer, the greeting `Instruction@` and `Despawn@` address that courier exactly; a stored RefID now registered under another name is stale and refused. Arrival and sightings use the courier's key in scan participants, and the name-only `reached_destination_player@` status counts only for an unshared name. Action-catalog inserts take the key from the resolved row, never from template data. Keyed readers (`chimIssuedOwnerClause()`, the catalog last-action map, Background Life worker reads, `DataLastAction($actor, $key)`, background events) filter by key before `LIMIT`; NULL legacy rows are kept but never adopted. Saves without the column gain it as NULL through the private stage upgrade.

`gamedata.php` follows the paired contract: each actor-bearing row (each bulk `statuses`/`states` entry on its own) may carry `actor_identity_version` 1, `actor_key` and `actor_refid` (8 uppercase hex). Any of these fields makes the row strict: an invalid version, key, RefID or type rejects the request with 422 before any write; the reserved `player` key is valid only with `actor_type` player and `00000014` and writes `core_player` only; a duplicate key or a row whose current RefID differs rejects a single-actor request with 409 (bulk rows are skipped); an unregistered explicit key on a single-actor request returns 409 (`unregistered_actor_key`) without creating a row, so the client's change-hash cache retries on its next refresh; 2xx means applied. Bulk requests return 200 with `{ok, applied, skipped, complete, rows:[{index, status: applied|skipped|noop, reason}]}`; `complete` is false whenever a row was skipped. `activity_status` rows may carry the C18 `attack_target_key`/`attack_target_refid` pair (both present; both null means no known target and drops any display name; otherwise a valid pair, else 422). The target binds to its exact row only while that row holds the captured RefID (`attack_target_binding` player, npc, unregistered, stale or none; `attack_target_npc_id`) and is never resolved by name. Keyed `low_process_actors.actors_nearby` entries are validated (pair grammar, RefID equal to `formId`, else 422) and kept in `low_process_actor_keys` beside the unchanged RefID-to-name map; Background Life nearby candidates resolve keyed entries by key and RefID with no name fallback. Writes go to the exact physical row's metadata with an atomic RefID guard (`updateMetadataKeysById(..., $expectedRefid)`), never to the linked profile owner, and `low_process_actors` no longer rewrites the whole row. Rows without identity fields keep the unique-name lookup; a typed player never writes an NPC namesake.

### Diaries and books

`data/diary_actor_identity.sql` (version `diary_actor_identity` 20260930001; `db_updates.php` and runtime readiness rerun it when an object is missing) adds `diarylog.author_key`, `books.book_key/author_key/recipient_key/reader_key/book_instance/content_version`, and `physical_npc_diaries.author_key`. The tracking table's old `npc_name` primary key is dropped; uniqueness is now `author_key` for keyed rows and `npc_name` among unassigned legacy rows. Nothing is backfilled: legacy rows keep NULL keys, remain visible to admins, and never match a runtime reader. Old saves restore into the upgraded table as unassigned rows (new nullable columns are added by `prepare_playthrough`).

- Writers (nearby/auto/manual/narrator diaries, player diary, Background Life journal notes) store `author_key` from the exact row captured before generation (`chimDiaryOwnerKey()`; `narrator`/`player` for typed principals). `chimDiaryAuthorStillCurrent()` re-reads the row after the LLM call and discards output when the physical key or profile binding changed. Linking never rewrites `author_key`.
- Readers use `chimDiaryReadKeys()`: the speaker's physical key plus explicitly linked profile members; the typed Narrator reads `narrator`; a physical NPC named "The Narrator" stays physical. Unrelated namesakes stay separate.
- Physical diary books are materialized per author (`chimPhysicalDiaryMaterialize($authorKey, ...)`), stored by `book_key = 'diary:' + author_key`, rendered with a key-based image name, and queued as `spawnBook@title@0@signedRecipientRef@task@b64:content@b64:identity`, where the optional 6th argument is `{identity_version:1, book_key, author_key, recipient_key}`. Titles carry no ids.
- `book.php` trusts upload identity (`book_key, author_key, recipient_key, book_instance, content_version`, `reader_key`) only for a `book_key` the server issued to that author, and only when `content_version` is the 16-hex FNV-1a 64 (`hash('fnv1a64')`, the client's `DiaryBookIdentityUtils::ContentHash`) of the exact body after the uploaded `Title: <title>
` line. An upload that sends `book_key` but fails any check gets 409 with no rows written; it never falls back to title ownership, generated-copy reuse, letter marking or read-request matching. Identity uploads keep their own content and correlate read requests by key, instance and version, never title. Ordinary books, notes and letters are unchanged.
- `book_read.class.php` captures `narrator_key`, `player_key`, `commenter_key` and `timeline` when a reading request is created. Delayed `Suggestion`/`Instruction` comments address a keyed physical commenter as `Name [RefID: XXXXXXXX]` (`bookReadCommenterSelector()`), so the enqueue hook records that row as the arg-0 target under the typed narrator envelope; the typed narrator and legacy unkeyed commenters keep their plain label. They are skipped when the captured commenter no longer resolves to the same row, when a legacy commenter name is shared by several NPCs, or when the playthrough changed. In auto-resume mode a skipped comment sets `resume_requested`, so reading continues instead of waiting for a comment that will never come. Reading innerchat rows use format 2 people with typed roles.
- `ui/api/chim_diaries.php`: `?list=people` returns `selector`, `author_key` (absent for legacy), `label`, `label_shared`, `legacy`; `?author_key=<key>[&group=1]` returns one author (or its linked group); `?person=<name>` returns only unassigned legacy rows; `?entry=` adds `author_key`/`author_label`. `chim_diary_audio.php` resolves the voice from the stored key (effective linked profile) and adds the key, playthrough and content hash to the cache seed; legacy names resolve only when unambiguous.

### Still name-based

`lookupLatestSpatialCompanionsByParticipant()` (builds legacy display name lists only), `processor/oghma.php`, the `analyze_relationships` preview, the NPC rename helper that rewrites legacy `companions` text, auto-diary profile/narrator-visibility helpers that take the display name, and Background Life name lookups with no exact key in scope. `resolveNpcByName()` (both handler copies) treats a canonical `ref:`/`dyn:` key, `Name [RefID: X]` or SpeakTo's `Name:refid` as authoritative: the RefID must be held by a row with that name, and a stale, recycled or foreign RefID is refused with no name fallback. A bare name resolves only when exactly one row has it; same-name actors are refused (MoveTo does not reinterpret them as a place, SpeakTo does not create a profile), and a trigram suggestion must pass the same rule. FindNPC/SpeakTo read factions and the dialogue profile from the routed row id via `backgroundLifeTargetProfile()`; only a profile just created for an unseen name uses `getByName()`. GiveGoldTo/SellService/trade arguments are `:`-separated, so they accept bare names only. Still name-based: the repeated-target teleport in `cmd/main.php` and `entrypoint.php` (the `actions_issued` destination is a name, so an ambiguous name stays unresolved), unkeyed nearby-actor descriptions in `cmd/main.php` and the `debug/simple_llm_request_with_context_life_v2.php` copy (unique names only), letter delivery (`lib/bgl_letters.php` uses the stored `npc_refid` while its holder has the letter's name, otherwise the unique name; a stored RefID held by another actor is not used, but one held by nobody still is), `chimBglResolveNpc()` (an unregistered RefID falls back by name only to an unbound legacy row) and creation reservations (`lib/background_life_npc_creation.php` refuses a name that several rows share). The non-JSON connectors no longer emit hardcoded `Herika|command|` lines: `openai`/`openrouter` use `chimBuildCurrentCommandLine()` and `koboldcpp`/`llamacpp`/`web_connector` use `chimBuildLegacyConnectorCommandLine()`/`chimRegisterLegacyConnectorCommand()`, so command lines carry the selected speaker's envelope or are dropped. Client routes without a captured identity (for example Papyrus-only events) stay legacy name-only rows.
